# 기준값과 근거

앱(web/index.html)이 쓰는 모든 숫자와 출처를 정리한다. 앱의 중심은 **단백질**이고, 칼로리는 사용자가 넣었을 때만 최대값으로 적용한다.

상태 표시는 세 가지다.
- **확인됨**: 출처에서 값을 직접 확인했다.
- **일부 확인**: 값의 일부만 확인했다. 원문을 다시 봐야 한다.
- **근거 없음**: 팀이 정했거나 사용자가 바꾸는 값이다. 발표 때 "제안"으로 밝힌다.

## 1. 하루 칼로리 (에너지 필요추정량) — 확인됨

미국 IOM(2002) 에너지 필요추정량 식을 쓴다. 한국인 영양소 섭취기준은 2005년판부터 이 식으로 계산하고, 한국인을 '저활동적'으로 본다. 그래서 앱의 활동 수준 기본값도 '저활동적'이다.

| 성별 | 식 (나이: 세, 체중: kg, 키: m) | 활동 계수 (비활동/저활동/활동/매우 활동) |
|---|---|---|
| 남 | 662 − 9.53×나이 + PA×(15.91×체중 + 539.6×키) | 1.0 / 1.11 / 1.25 / 1.48 |
| 여 | 354 − 6.91×나이 + PA×(9.36×체중 + 726×키) | 1.0 / 1.12 / 1.27 / 1.45 |

- 한국인 섭취기준이 IOM 식을 쓴다는 근거: https://koreascience.kr/article/JAKO202108360693676.page?lang=ko
- 식과 계수: https://www150.statcan.gc.ca/n1/pub/82-003-x/2008004/article/10703/t/5800493-eng.htm
- 한계: 성인용 식이라 19세 이상만 계산한다. 2025 개정판에서 식이 바뀌었는지는 원문으로 확인하지 못했다.
- 쓰는 곳: 체중 줄이기 목표의 칼로리 최대값만 이 값으로 정한다(3번).

## 2. 하루 단백질 (목표별)

| 목표 | 값 | 상태 | 출처 |
|---|---|---|---|
| 건강 유지 | 0.91 g/kg | 일부 확인 | 2020 한국인 영양소 섭취기준 권장섭취량. 평균필요량은 0.73 g/kg, 변이계수는 12.5%다. https://www.koreascience.or.kr/article/JAKO202210242857035.page — 2025 개정판의 성인 값은 원문으로 확인하지 못했다. |
| 근육 늘리기 | 1.4 g/kg | 확인됨 | ISSN 입장문(Jäger 외, 2017)은 운동하는 사람에게 1.4~2.0 g/kg를 권한다. https://pubmed.ncbi.nlm.nih.gov/28642676/ |
| 체중 줄이기 | 1.6 g/kg | 확인됨 | Hector & Phillips(2018)는 감량 중 1.6~2.4 g/kg를 권한다. 운동선수 대상 연구다. https://pubmed.ncbi.nlm.nih.gov/29182451/ |

범위의 하한을 고른 것은 **팀 선택**이다. 최저가를 찾는 문제라서, 근거 범위 안에서 가장 적은 값을 쓰면 비용이 가장 적게 든다.

## 3. 칼로리 조건

### 칼로리 최소 — 없음 (팀 결정)
최소 칼로리는 두지 않는다. 알고리즘에는 0을 넘긴다.

### 칼로리 최대 — 입력할 때만 적용 (팀 결정)
칼로리 최대는 사용자가 입력할 때만 적용한다. 비워 두면 상관없음이고, 알고리즘에는 무한대를 넘긴다.

### 체중 줄이기 목표의 칼로리 최대 — 확인됨
- 한 끼 최대 = (에너지 필요추정량 − 500 kcal) ÷ 끼니 수를 10 kcal 단위로 반올림한 값이다.
- 근거: Murphy, Hector & Phillips(2015)는 근육을 지키며 감량하려면 하루 약 500 kcal의 중간 정도 적자를 두라고 권한다. https://pubmed.ncbi.nlm.nih.gov/25014731/
- 근육 늘리기와 건강 유지는 칼로리를 제한하지 않는다. 근육을 늘리려면 칼로리를 막을 이유가 없고, 앱은 단백질에 집중한다.

## 4. 끼니로 나누기 — 확인됨

한 끼 단백질은 ⌈하루 단백질 ÷ 끼니 수⌉로 계산하고, 끼니 수는 2·3·4 중에 고른다.

ISSN 입장문은 하루 단백질을 3~4시간 간격으로 고르게 나누라고 하고, 1회 0.25 g/kg(약 20~40 g)를 권한다. 앱은 이 값을 참고로 보여 주고, 한 끼 목표가 그보다 적으면 안내한다.

## 5. 내 정보가 없을 때 — 단백질 기본값 없음 (팀 결정, 2026-11-25)

기본 단백질 목표는 두지 않는다. 예전의 34 g(하루 2,000 kcal × 20% ÷ 3끼)은 3끼 같은 팀 결정이 섞여 있어서 없앴다.

단백질 칸이 비어 있으면 조합을 찾지 않고 안내만 보여 준다. 사용자는 두 방법 중 하나로 목표를 정한다.
- 단백질 칸에 직접 넣는다.
- '내 정보'를 넣어 2번의 근거로 계산한다.

## 5-1. 정렬 — 최저가 하나 (팀 결정 2026-11-25)

조합은 예산 안의 모든 조합 중 **가격이 싼 순서**로만 보여 준다. 처음에 20개를 보여 주고, 아래로 내리면 20개씩 더 보여 준다.

- **없앤 정렬**: 단백질 많은 순, 칼로리 낮은 순, 1g당 싼 순(예전 이름 '가성비')
- **이유**: 앱의 기준을 최저가 하나로 단순하게 맞추었다.
- **코드**: web/algo.js의 bnbTopK에서 이 세 기준으로 찾던 코드도 지웠다. 이제 bnbTopK는 최저가 순서만 찾는다.
- **검증**: 지운 뒤 행사 상품(1+1·2+1의 개수별 행)을 섞은 무작위 400가지 경우를 모든 경우를 따진 결과와 비교했고, 모두 같았다.

## 6. 가격과 1+1·2+1 행사 — 확인됨 (CU 데이터)

- 정가, 행사 표시(1+1, 2+1), 상품 분류는 CU 홈페이지 상품 목록에서 수집했다(scripts/collect_cu.py).
- 계산은 CU 행사 규칙 그대로다. 1+1은 정가 1개 값에 2개, 2+1은 정가 2개 값에 3개를 받는다. 영양 값도 받는 개수만큼 곱했다(scripts/select_items.py).
- **웹 앱 (팀 결정 2026-11-25)**: 행사 상품은 적게 사는 행도 둔다(data/selected/web_items.csv).

  | 행사 | 선택지 (받는 개수: 내는 값) |
  |---|---|
  | 1+1 | 1개: 1개 값 / 2개: 1개 값 |
  | 2+1 | 1개: 1개 값 / 2개: 2개 값 / 3개: 2개 값 |

  - 같은 상품의 행들은 한 조합에 하나만 들어간다. 탐색, 바꿔 담기, 꼭 넣기, 빼기에서 모두 막는다.
  - 같은 모양으로 묶는 기준(유형과 가격)에 받는 개수도 넣었다. 그래서 값이 같아도 개수가 다르면(예: 2+1의 2개와 3개) 다른 조합으로 보인다.
  - 행 수: 상품 1,315개, 행 2,032개.
    - 1+1 161개에 1개 행 추가
    - 2+1 278개에 1개 행과 2개 행 추가
  - 최저가 목록에서 1+1의 1개와 2+1의 2개는 잘 나오지 않는다. 같은 값으로 더 많이 받는 행사 묶음이 항상 앞서기 때문이다. 주로 칼로리 최대를 정했을 때나 '꼭 넣기'로 직접 골랐을 때 나온다.
  - 검증: 행사 상품을 섞은 400가지 경우를 모든 경우를 따진 결과와 비교했고, 모두 같았다. 같은 상품이 두 번 들어간 조합은 0개였다.
- **Python 실험용** experiment_items.csv는 상품당 1행 그대로 둔다(행사 상품은 묶음 행만). Greedy, DP, B&B 비교는 지금처럼 0/1 문제로 한다.
- 행사는 보통 매월 바뀐다. 앱은 수집 날짜를 함께 보여 준다.

## 7. 화면 기본값 — 근거 없음

| 값 | 설명 |
|---|---|
| 예산 기본 10,000원, 슬라이더 2,000~30,000원 | 사용자가 바로 바꾸는 값 |
| 조합 보여주기: 처음 20개, 아래로 내리면 20개씩 더, 최대 200개 | 화면 기본값 |
| 개수 조건 최대 10개 | 화면 제한 |
| B&B 시간 제한 4초 | 화면이 멈추지 않게 둔 값 |

## 8. 없앤 기준 (2026-11-25)

- **없앤 항목**: 당류·나트륨 경고, '당류 낮게'·'나트륨 낮게' 버튼, 칼로리 최소, 칼로리 허용폭 ±10%(근거 없던 값), 기본 단백질 34 g
- **이유**: 앱의 기준을 단백질에 집중하기 위해서다.
- **남은 기능**: '영양 조건' 창에서 탄수화물·지방·당류·나트륨 상한을 직접 넣을 수 있다. 사용자가 넣는 값이라 근거가 필요 없다.

## 8-1. 알고리즘 비교 실험 설정 — 근거 없음 (제안, 2026-11-25)

scripts/run_experiment.py가 쓰는 값이다. 결과는 web/compare.html(알고리즘 비교 페이지)에서 본다.

| 값 | 설정 | 이유 |
|---|---|---|
| 상품 수 n | 10, 20, 30, 40, 50, 100, 200, 500, 1000, 전체(1,315) | 팀 지시문의 n = 10~50 구간과, 실제 데이터 크기까지 |
| 시드 | n마다 5개 (전체는 1개) | 한 부분집합만 보면 우연에 좌우되기 때문이다 |
| 시간 | 3번 돌려 중앙값. 한 번에 0.5초를 넘으면 1번만 | 짧은 측정은 잡음이 크다 |
| 메모리 | tracemalloc 최대치, n마다 첫 시드만 | tracemalloc을 켜면 DP가 몇 배 느려진다 |
| 완전탐색 대조 | n ≤ 10 | 2¹⁰ = 1,024개라 Python으로도 금방 끝난다 |
| B&B 시간 제한 | 30초 | 넘으면 '최적 보장 안 됨'으로 기록한다 |
| 실험 조건 5개 | 가벼운 한 끼(≥20g, 300~500kcal) 등 | 실험용 입력 조건이다. 영양 권장량이 아니다 |

- 실험은 보고서의 수학 모델(칼로리 최소~최대)을 그대로 쓴다. 웹 앱은 칼로리 최대만 쓴다(3번). 둘이 다른 점을 보고서에 밝힌다.
- 11-24 실험(상품 1,322개)은 데이터를 정리하기 전 결과라서, 현재 데이터(1,315개)로 다시 돌렸다.

## 9. 데이터 결정 — 팀 결정

- **영양 값**: 식약처 가공식품 영양성분 DB를 제품명으로 매칭했다. 매칭 등급은 다음과 같다.
  - A: 제품명과 용량이 모두 일치
  - B: 제품명은 일치, 용량은 추정
  - B-: 비슷한 제품명으로 매칭
- **뺀 상품**: 묶음 상품, 값이 이상한 상품(예: 200 g 묶음 값이 들어간 스트링치즈), 조미료, 가스레인지로 조리해야 하는 상품은 뺐다. 전자레인지 조리는 허용한다.
